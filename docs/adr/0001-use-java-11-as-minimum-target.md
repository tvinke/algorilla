# ADR-0001: Use Java 11 as minimum runtime target

**Status**: Accepted

**Date**: 2026-03-06

## Context

Algorilla is a static analysis CLI tool that targets JVM codebases. To maximize adoption, we want to support the oldest Java version that developers are likely to have on their machines, while still being able to leverage the latest Gradle and Kotlin features for development.

The project uses Kotlin 2.1, Gradle 8.12, and several libraries including logback 1.5.x, ANTLR 4.13, picocli 4.7, and kaml 0.67. We need to determine the lowest JVM bytecode target that is compatible with all dependencies.

Key constraints from the dependency chain:

| Dependency | Minimum Java version |
|---|---|
| Kotlin 2.1.10 (compiler target) | 8 |
| Gradle 8.12 (toolchain target) | 8 |
| logback 1.5.x | **11** |
| kotlin-logging 7.x | 8 |
| ANTLR 4.13 | 8 |
| picocli 4.7 | 5 |
| kaml 0.67 | 8 |
| JUnit 5.11 / kotest 5.9 | 8 |

The binding constraint is logback 1.5.x, which requires Java 11 at runtime.

Candidates considered:

- **Java 8**: Maximum theoretical reach, but blocked by logback 1.5.x without a downgrade. Java 8 is also increasingly rare on developer machines.
- **Java 11**: Oldest LTS still commonly installed. All current dependencies support it. No compromises needed.
- **Java 17**: Current mainstream LTS with wide enterprise adoption, but unnecessarily narrows the audience.
- **Java 21**: Latest LTS. Too restrictive for a tool that aims for broad adoption.

## Decision

Set `jvmTarget` to Java 11 for all modules. Keep `jvmToolchain` at 21 so that the project builds with a modern JDK but produces bytecode compatible with Java 11.

This means:
- Users can run Algorilla on Java 11 or higher.
- Developers building Algorilla need JDK 21 (auto-provisioned by Gradle toolchains).
- No dependency changes are required.

## Consequences

- Algorilla can be used on any machine with Java 11+, covering the vast majority of active JVM installations.
- We cannot use Java 17+ APIs (records, sealed classes, pattern matching) in generated bytecode. This is irrelevant since the codebase is Kotlin — the Kotlin compiler handles its own bytecode generation.
- If a future dependency raises its minimum to Java 17, this ADR should be superseded.
- The split between toolchain (21) and target (11) is standard Gradle practice and does not add build complexity.
